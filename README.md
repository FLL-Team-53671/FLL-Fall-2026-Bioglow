# Cobra Bytes: Fall 2026 BIOGLOW

Cobra Bytes (FLL Team 53671) code for Fall 2026.

This is based on MrGibbage's tutorial for using PyBricks, VS Code, and GitHub
for FLL. Read the full tutorial here:
https://github.com/MrGibbage/fll-pybricks-vscode-tutorial?tab=readme-ov-file

## Code Structure

| File | Purpose |
| --- | --- |
| `master_program.py` | **Main entrypoint.** Runs on the hub. Shows a hub menu to pick which program to run (e.g. Xbox remote control or a mission) and instantiates the current robot before launching it. |
| `base_robot.py` | `BaseRobot` class with shared functionality: drive-base helpers (`driveForDistance`), attachment/arm motor methods. Not meant to be run directly. |
| `robots.py` | One robot class per physical robot design (e.g. `AdvancedDrivingBaseRobot`, `PiRobot`), plus the `ROBOT_CONFIG` dictionary that maps robot **names** to robot classes. Add a new entry here when configuring a new robot. |
| `current_robot.py` | `current_robot()` helper: reads the robot name from `current_robot_name.py`, looks it up in `ROBOT_CONFIG`, and instantiates it once. Silently falls back to a bare `BaseRobot` (with a printed warning) if the name is not in `ROBOT_CONFIG`. |
| `current_robot_name.py` | **Autogenerated — do not edit.** Contains `ROBOT_NAME = "..."` and is rewritten on every launch by the VS Code tasks. Gitignored. |
| `xbox_remote_control.py` | Driver program: remote-control the robot with an Xbox controller. |
| `sample_mission1.py` | Example mission program: one `run(robot)` function with a short demo drive. Create one of these per mission. |
| `help/` | Reference material: build instruction PDFs, PyBricks API PDF, VS Code tutorial, and a `.code-profile` for VS Code on the hub. |
| `.vscode/tasks.json` | VS Code task definitions: how programs are launched on the robot and how `current_robot_name.py` is generated. |

## How a Launch Works (e.g. Ctrl-L)

1. The VS Code task "Run master_program.py on my robot" first runs the
   "Write my robot name to current_robot_name.py" task, which regenerates
   `current_robot_name.py` from the robot name setting.
2. It then runs `pybricksdev run ble --name <robot name> master_program.py`,
   which deploys the program to the hub over Bluetooth.
3. On the hub, `master_program.py` shows a menu; `current_robot()` builds the
   robot object from the name in `current_robot_name.py`.

## Where the Robot Name Is Configured

The robot name (used both for the BLE connection and for `ROBOT_CONFIG`
lookup) comes from the **`fllRobotName`** VS Code setting:

- **Global user settings (the default place):**
  `~/Library/Application Support/Code/User/settings.json`
  ```json
  "fllRobotName": "PezBot"
  ```
  Open with Cmd+, in VS Code and search for `fllRobotName`.
- An optional workspace setting (`.vscode/settings.json`) can override the
  global one if you want a different robot name per repo.

The name you set must match a key in `ROBOT_CONFIG` in `robots.py`, and it
should also match the hub's Bluetooth name (the `--name` argument of
`pybricksdev run ble`).

## Flashing PyBricks Firmware

If the hub has the stock LEGO firmware, flash PyBricks first: connect the hub
by USB, then run `./.venv/bin/pybricksdev flash` (add `--version <x.y.z>` to
pin a specific firmware version). See the PyBricks docs for details.
